# Finish plan

Use this skill only after the user explicitly writes `$finish-plan`. This is the only harness skill that may commit and push.

1. Confirm the current branch is `dev` and run `node tools/harness/cli.mjs validate` plus `node tools/harness/cli.mjs status`. Validation covers the root plan catalog and the selected plan's local task index. Use a plan ID explicitly named by the user. If none is named, select the last `status: "completed"` entry in `_docs/plans/index.json` as the most recently completed plan. Check `git branch -vv`, `git remote get-url --push origin`, and `git status --short` to identify the tracked branch, actual push destination, and every file the CLI will commit. State the destination and branch before running `finish`.
2. Treat the user's explicit `$finish-plan` invocation as authorization to commit and push to the verified existing upstream when it matches the established project destination. Do not require the user to repeat that repository URL on each invocation. If the push remote or upstream is missing, has changed, or conflicts with the user's stated destination, resolve that discrepancy before publishing. Run `node tools/harness/cli.mjs finish --plan <id> [--message "..."]` directly. On the first attempt, invoke the command through Codex `exec_command` with `sandbox_permissions: "require_escalated"` so it can write `.git/index.lock` for the commit; this is a tool permission setting, not a CLI flag. Include the verified push URL, branch, plan ID, changed-file scope, and user's `$finish-plan` authorization in the escalation justification. The default commit message is `finish <plan-id>`, where `<plan-id>` is the selected plan's `id`; an explicit `--message` overrides it. Do not substitute manual Git commands or bypass a rejected approval review; if review still rejects the push, report its reason and request the specific approval it requires.
3. The CLI runs declared checks only for tasks whose files target `front/` or `back/`, plus the relevant front/back full checks. It does not reject dirty files outside those check scopes; all non-ignored Git changes are staged and committed, including `_docs/plans` and Harness files. Gitignored files remain untracked and are not committed.
   Backend `test` includes real HTTP API tests through Postman CLI. Before running `finish`, verify that the development server reflects the current code and meets `back/test/api/README.md` prerequisites. Missing server/data is a failed check, not a reason to skip API verification or modify existing database records.
4. Report the commit/push outcome and any check failure exactly. Do not retry a failed validation by widening task files without a new approved `$harness-plan` revision.
