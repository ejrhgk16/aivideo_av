# 분석 이벤트 수집 API

> 상태: 제안. 아직 구현되지 않았다. 관리자 지표 정의서 초안 v0.1(2026-11-25)의 확정 결정을 따른다. 정의서는 저장소 밖에서 관리하며, 이 계약에 필요한 결정은 [Analytics README](README.md#지표-정의-요약)와 이 문서에 모두 옮겼다. 정의서의 [미정] 항목은 정의서의 추천안을 따르고 본문에 `추천`으로 표시한다. 이 문서에서 새로 정한 조정 가능한 운영 값은 `제안값`으로 표시한다.

## POST /analytics/events

앱이 모은 빼꼼 노출과 본편 재생 이벤트를 한 요청에 최대 50개씩 받아 원본 테이블에 저장한다. 비로그인 사용자도 설치 ID로 보낼 수 있다. 저장 결과는 응답하지 않으며, 관리자 지표는 서버가 매일 만드는 일별 집계에서 읽는다.

### 인증

선택적 JWT 인증이다. `Authorization` 헤더가 없으면 익명이고, 헤더가 있으면 유효한 Access JWT가 필요하다. Refresh token은 사용할 수 없다. 잘못된·빈 헤더, Refresh token, 만료 또는 변조된 Access는 `AUTH_INVALID_TOKEN`(401)이며 익명으로 다시 처리하지 않는다.

- 검증된 JWT 사용자는 이 요청으로 새로 저장하는 노출 행의 `user_id`가 된다. 요청 본문이나 query로 사용자를 지정할 수 없다.
- 재생 세션의 사용자는 세션을 발급한 재생 API 요청의 JWT로 이미 정해져 있다. 이 API의 JWT로 바꾸지 않는다.
- 기기는 본문의 `installId`로 구분한다. 설치 ID는 인증 수단이 아니며 사용자를 선택하지 않는다.

### Request body

헤더: `Content-Type: application/json`, 선택 `Authorization: Bearer <accessToken>`

```json
{
  "installId": "3f6c1d2a-8b4e-4c7f-9a1d-2e5b7c9d0f13",
  "sentAt": "2026-11-25T03:00:10.000Z",
  "events": [
    {
      "eventId": "0b9e4f6a-1c2d-4e3f-8a5b-6c7d8e9f0a1b",
      "type": "feed_impression",
      "occurredAt": "2026-11-25T02:59:01.200Z",
      "dramaUuid": "00000002-0000-4000-8000-000000000001",
      "feedPosition": 3
    },
    {
      "eventId": "5a7c2e14-93d1-4b6f-a0e8-7f2c4d9b1e35",
      "type": "playback_start",
      "occurredAt": "2026-11-25T02:59:20.000Z",
      "playbackSessionId": "9d8c7b6a-5f4e-4d3c-8b2a-1f0e9d8c7b6a"
    },
    {
      "eventId": "c2e81f47-6b3a-4d95-8e07-1a4f9c3b2d68",
      "type": "playback_progress",
      "occurredAt": "2026-11-25T02:59:30.000Z",
      "playbackSessionId": "9d8c7b6a-5f4e-4d3c-8b2a-1f0e9d8c7b6a",
      "watchedMs": 10000,
      "maxReachedMs": 10000
    },
    {
      "eventId": "7e4d0b92-2f5c-4a18-b6e3-9c1a7f0d4e52",
      "type": "playback_end",
      "occurredAt": "2026-11-25T03:00:05.000Z",
      "playbackSessionId": "9d8c7b6a-5f4e-4d3c-8b2a-1f0e9d8c7b6a",
      "watchedMs": 44500,
      "maxReachedMs": 45000
    }
  ]
}
```

| 필드 | 필수 | 타입 | 설명 |
| --- | --- | --- | --- |
| `installId` | 예 | string | 앱 설치(웹은 브라우저 저장소)마다 처음 실행할 때 만드는 무작위 UUID v4. 로그인·로그아웃해도 바뀌지 않는다. 기기 고유번호나 광고 ID를 쓰지 않는다. |
| `sentAt` | 예 | string | 앱이 이 요청을 보내는 기기 시각. ISO 8601 UTC(`Z`). 재전송할 때도 보내는 시도마다 새로 정한다. 기기 시계 보정에 쓴다. |
| `events` | 예 | array | 1~50개의 이벤트 |

모든 이벤트의 공통 필드:

| 필드 | 필수 | 타입 | 설명 |
| --- | --- | --- | --- |
| `eventId` | 예 | string | 앱이 이벤트마다 만드는 UUID v4. 재전송 중복 방지와 앱 전송 큐의 키 |
| `type` | 예 | string | `feed_impression`, `playback_start`, `playback_progress`, `playback_end` |
| `occurredAt` | 예 | string | 이벤트가 일어난 기기 시각. ISO 8601 UTC(`Z`) |

`feed_impression` 필드:

| 필드 | 필수 | 타입 | 설명 |
| --- | --- | --- | --- |
| `dramaUuid` | 예 | string | 노출된 빼꼼 카드의 작품 UUID |
| `feedPosition` | 예 | integer | 빼꼼 피드에서 카드 순서. 1부터 시작하며 1~1000 |

`playback_start` 필드:

| 필드 | 필수 | 타입 | 설명 |
| --- | --- | --- | --- |
| `playbackSessionId` | 예 | string | [재생 세션 ID 발급](#재생-세션-id-발급)에서 받은 세션 ID |

`playback_progress`, `playback_end` 필드:

| 필드 | 필수 | 타입 | 설명 |
| --- | --- | --- | --- |
| `playbackSessionId` | 예 | string | 재생 세션 ID |
| `watchedMs` | 예 | integer | 이 세션에서 실제로 재생된 시간의 누적 밀리초. 0~2147483647 |
| `maxReachedMs` | 예 | integer | 실제 재생으로 도달한 가장 먼 위치(밀리초). 앞으로 건너뛴 위치는 넣지 않는다. 0~2147483647 |

재생 이벤트에는 작품·회차·영상 UUID를 보내지 않는다. 서버가 세션을 발급할 때 이미 정했기 때문이다. 5% 도달 구간도 보내지 않는다. 서버가 `maxReachedMs`와 세션의 영상 길이로 계산한다. 정의되지 않은 필드는 무시한다.

### 재생 세션 ID 발급

재생 세션 ID는 `playback_start`의 응답이 아니라 회차 재생 URL API가 발급한다. 아래 응답 변경도 제안이며, 구현할 때 같은 작업에서 [회차 재생 API](../04-playback/episodes.md) 문서에 반영한다([구현할 때 같이 고칠 곳](#구현할-때-같이-고칠-곳)).

```json
{
  "url": "https://aivideo-dev.s3.ap-northeast-2.amazonaws.com/...?...",
  "videoUuid": "00000004-0000-4000-8000-000000000101",
  "playbackSessionId": "9d8c7b6a-5f4e-4d3c-8b2a-1f0e9d8c7b6a",
  "durationMs": 420000
}
```

- `GET /episodes/:episodeId/playback`의 200 응답에 `playbackSessionId`(UUID v4 문자열 또는 `null`)를 더한다. 위 예시는 더하는 필드 주변만 보인 것이며 기존 필드는 바꾸지 않는다.
- 이 응답은 `Cache-Control: no-store`다. 프록시나 CDN이 응답을 저장해 세션 ID 하나를 여러 재생에 돌려주지 않게 하기 위해서다.
- 서버는 공개·구매 권한 검사를 통과해 URL을 발급할 때마다 `playback_sessions`에 행 하나를 만든다. 행에는 선택된 FULL 영상, 회차, 작품, 응답한 `durationMs`, 선택적 JWT 사용자(익명은 NULL), 발급 시각을 저장한다. 오류 응답에서는 발급하지 않는다.
- 같은 클라이언트 IP의 세션 발급이 1분에 60개를 넘으면 세션을 만들지 않고 `playbackSessionId`를 `null`로 응답한다(제안값). URL은 그대로 발급해 재생을 막지 않는다. 앱은 `null`이면 그 재생의 이벤트를 보내지 않는다. 무료 회차는 익명으로도 세션을 받으므로, 이 한도가 없으면 세션을 계속 받아 조회를 만들어 낼 수 있다. IP 처리는 [요청 제한](#요청-제한)을 따른다.
- 프리뷰 재생 API(`GET /dramas/:dramaId/previews/:videoId/playback`)는 세션을 발급하지 않는다. 빼꼼 쇼츠와 미리보기 재생은 조회수에 넣지 않는다.
- 앱은 재생 화면이 포커스된 동안 받은 세션 ID를 그 화면의 재생 이벤트에 계속 쓴다. 같은 세션 안에서 장면을 넘기는 것은 새 조회가 아니다. 화면이 포커스를 잃으면 `playback_end`를 보내고 그 세션을 닫는다. 작품 소개·회차 목록 같은 다른 화면에서 돌아와 재생 화면이 다시 포커스되면 재생 API를 다시 불러 새 세션 ID를 받는다. 응답의 `videoUuid`가 재생 중인 영상과 같으면 영상을 다시 불러오지 않아도 된다. 30초 안에 돌아오면 일별 집계에서 앞 조회에 합친다. 회차를 닫았다가 다시 열거나 로그인 상태가 바뀌어 재생 정보를 다시 받을 때도 새 세션 ID를 쓴다. 재생되지 않은 세션은 조회가 아니며 90일 뒤 지워진다.

이렇게 정한 이유:

- 앱은 재생 전에 반드시 이 API를 부르고, 서버는 여기서 이미 공개·구매 권한을 확인한다. 같은 자리에서 세션을 만들면 어떤 영상의 재생인지 서버가 정하므로 클라이언트가 영상을 바꿔 보낼 수 없다. 정의서의 "서버가 발급하지 않은 재생 세션은 걸러 낸다"도 세션 존재 여부로 확인된다.
- 세션 ID를 재생 전에 알고 있으므로 시작·진행·종료 이벤트를 모두 같은 묶음 전송과 오프라인 재전송으로 보낼 수 있다. `playback_start`의 응답으로 받으려면 시작 이벤트만 즉시 따로 보내야 하고, 오프라인에서는 세션을 만들 수 없으며, 이 API가 이벤트별 결과를 응답해야 한다.
- 기존 응답에 필드 하나를 더하는 하위 호환 변경이다.
- 대신 GET 요청이 행을 만든다. 요청마다 새 서명 URL을 만드는 응답이고 `no-store`로 캐시를 막으며 재생 직전에만 호출되므로 받아들인다.
- 본편 재생 API와 프리뷰 재생 API는 지금 개발 환경에서만 동작한다. 운영 재생 경로(본편과 프리뷰 모두)가 선행 조건이다. 본편 경로가 없으면 운영에서 세션이 발급되지 않아 재생 이벤트가 모두 버려진다. 프리뷰 경로가 없으면 빼꼼 쇼츠가 재생되지 않으므로 노출('쇼츠가 화면에 뜬 횟수')과 조회율의 의미도 운영 미디어 경로에 달려 있다. 운영 재생 경로가 이 API를 거치지 않으면 발급 위치를 다시 정한다.

### 검증과 처리

서버는 아래 순서로 처리한다.

1. 묶음 형식을 검사한다. 실패하면 묶음 전체를 `HTTP_BAD_REQUEST`(400)로 거부하고 아무것도 저장하지 않는다.
2. 이벤트마다 형식을 검사한다. 맞지 않는 이벤트만 버린다.
3. 기기 시각을 보정하고 시간 범위를 확인한다. 범위를 벗어난 이벤트만 버린다.
4. 이벤트별 내용을 확인한다. 조건에 맞지 않는 이벤트만 버린다.

버린 이벤트가 있어도 응답은 204이며 버린 개수나 사유를 알려 주지 않는다.

#### 형식 검사

묶음 전체가 400인 경우: 본문이 객체가 아니거나 `installId`·`sentAt`·`events`가 없을 때, `installId`가 UUID 형식이 아닐 때, `sentAt`이 `Z`로 끝나는 ISO 8601 시각이 아닐 때, `events`가 배열이 아니거나 0개이거나 50개를 넘을 때.

그 이벤트만 버리는 경우: 이벤트가 객체가 아닐 때, `eventId`·`playbackSessionId`·`dramaUuid`가 UUID 형식이 아닐 때, `occurredAt`이 `Z`로 끝나는 ISO 8601 시각이 아닐 때, `type`이 네 값 중 하나가 아닐 때, 해당 `type`의 필수 필드가 없거나 정수 필드가 정수가 아니거나 범위를 벗어날 때. 앱이 서버보다 먼저 새 이벤트 타입을 보내도 같은 묶음의 다른 이벤트는 저장된다.

#### 시계 보정과 시간 범위

- 서버는 수신 시각과 `sentAt`의 차이를 같은 묶음의 모든 `occurredAt`에 더한다. 보정 시각은 `occurredAt + (수신 시각 − sentAt)`이다. 기기 시계가 틀려도 이벤트 사이의 간격은 유지된다.
- 보정 시각이 수신 시각보다 늦으면 수신 시각으로 본다.
- 보정 시각이 수신 시각보다 48시간 넘게 이른 이벤트는 버린다. 일별 집계는 최근 3일을 다시 계산하므로 늦게 온 이벤트도 대부분 반영된다. 빠질 수 있는 경우는 [데이터 모델 제안](data-model-proposal.md#일별-집계-작업)을 본다.
- 저장하는 시각은 모두 보정 시각(UTC)이다.

#### feed_impression

- `dramaUuid`가 공개 작품(`status = PUBLISHED`, `published_at`이 현재 시각 이하)이 아니면 버린다.
- `eventId`가 이미 저장돼 있으면 다시 저장하지 않는다. 같은 묶음 안의 중복도 같다.
- `eventId`, `installId`, JWT 사용자, 작품, `feedPosition`, 보정 시각을 노출 원본으로 저장한다.
- 같은 기기의 30분 반복 노출 제거와 24시간 전환 판정은 일별 집계에서 한다. 원본은 받은 그대로 저장한다.

#### playback_start, playback_progress, playback_end

- 발급되지 않은 세션 ID의 이벤트는 버린다.
- 세션의 설치 ID는 처음 반영된 묶음의 `installId` 하나로 정해지고, 다른 설치 ID로 온 이벤트는 버린다. 묶음 두 개가 동시에 들어와도 하나만 정해지도록 설치 ID 확인과 아래 값 갱신을 세션 행에 대한 UPDATE 한 문으로 한다. `install_id`가 NULL이거나 이 묶음의 값과 같은 행만 갱신하고, 갱신된 행이 없으면 그 이벤트를 버린다. 읽은 값을 고쳐 다시 쓰지 않는다.
- 보정 시각을 세션 발급 시각과 수신 시각 사이로 자른다.
- 세션에 종료 시각이 있으면 그보다 늦은 이벤트는 버린다. 정상 앱은 종료한 세션에 이벤트를 보내지 않으므로 숨은 화면의 잘못된 전송만 걸러진다.
- `watchedMs`는 세션 발급 뒤 지난 시간(수신 시각 − 발급 시각)을 넘지 않게, `maxReachedMs`는 세션의 영상 길이를 넘지 않게 자른다.
- 세션 행 하나에 아래 값을 갱신한다. 종료 뒤 이벤트를 버리는 규칙을 빼면 모든 값이 한 방향으로만 바뀌므로 재전송·중복·순서 뒤바뀜에도 결과가 같다. 재생 이벤트의 `eventId`는 저장하지 않는다.

| 값 | 갱신 |
| --- | --- |
| 시작 시각 | `playback_start`, 또는 `watchedMs`나 `maxReachedMs`가 0보다 큰 `playback_progress`·`playback_end` 중 가장 이른 시각 |
| 마지막 재생 시각 | `watchedMs`가 저장된 값보다 큰 이벤트의 시각. 0이 아닌 같은 값이 더 이른 시각으로 오면 이른 시각 |
| 마지막 이벤트 시각 | 받은 재생 이벤트 중 가장 늦은 시각 |
| 종료 시각 | 받은 `playback_end` 중 가장 이른 시각 |
| `watchedMs`, `maxReachedMs` | 받은 값 중 큰 값 |

- `playback_start`가 유실돼도 실제 재생 값이 있는 `playback_progress`나 `playback_end`가 오면 재생이 시작된 세션으로 본다. 값이 0인 종료 이벤트만 온 세션(첫 장면 전에 떠난 경우)은 시작 시각이 없어 조회가 아니다.
- 마지막 재생 시각은 `watchedMs`가 실제로 늘어날 때만 바뀐다. 일시정지한 뒤 백그라운드 전환이나 화면 이탈로 보낸 이벤트는 이 시각을 늘리지 않는다.
- 기존 [시청기록 저장](../04-playback/watch-progress.md) API와 2/3 완료 기준은 바꾸지 않는다.

조회 판정, 동시 재생·30초 안 다시 열기 처리, 완주·도달 구간 계산은 일별 집계 규칙을 따른다. [데이터 모델 제안](data-model-proposal.md#조회-판정)을 본다.

#### 요청 제한

- 한 요청의 이벤트는 50개까지다. 본문이 서버의 JSON 크기 한도를 넘으면 `HTTP_PAYLOAD_TOO_LARGE`(413)다.
- 같은 `installId`의 요청이 1분에 30회를 넘으면 `HTTP_TOO_MANY_REQUESTS`(429)다(제안값). 정상 앱은 10~15초마다 한 번과 화면 전환 때 보내므로 이 한도에 닿지 않는다. 이 한도는 정상 앱의 전송 폭주를 막는 것이며 위조 방지가 아니다. 설치 ID는 앱이 정하는 값이라 요청마다 바꾸면 이 한도와 30분 노출 중복 제거, 30초 병합, 동시 재생 제외를 모두 피할 수 있다.
- 위조 반복은 클라이언트 IP 기준으로 막는다. 같은 IP의 이 API 요청이 1분에 300회를 넘으면 429다(제안값). 세션 발급은 [재생 세션 ID 발급](#재생-세션-id-발급)의 IP 한도를 따른다.
- IP는 요청 제한 카운터에서만 잠깐 쓰고 저장하지 않는다. 서버는 프록시 뒤에서 실제 클라이언트 IP를 읽도록 신뢰할 프록시를 설정한다(Express `trust proxy`).
- 백엔드는 여러 서버리스 인스턴스로 실행되므로([인증 방식](../00-overview/authentication.md)) 인스턴스 메모리 카운터를 쓰지 않는다. 공유 저장소의 카운터나 배포 플랫폼의 요청 제한을 쓰며, 어느 쪽을 쓸지는 구현할 때 정한다.
- 통신사 망처럼 여러 사용자가 한 IP를 함께 쓰면 정상 사용자도 IP 한도에 닿을 수 있다. IP 한도 값은 운영 트래픽을 보고 다시 정한다.

### 204 Response

저장한 이벤트가 없어도 본문 없는 `204 No Content`를 반환한다.

### Errors

모든 오류는 `{ errorCode, errorName, statusCode, timestamp, path }`의 공통 형식이다.

| HTTP | errorCode | errorName | 의미 |
| --- | --- | --- | --- |
| 400 | `HTTP_BAD_REQUEST` | `BAD_REQUEST` | 묶음 형식 오류(`installId`·`sentAt`·`events`). 묶음 전체를 저장하지 않음 |
| 401 | `AUTH_INVALID_TOKEN` | `InvalidToken` | `Authorization` 헤더가 있지만 유효한 Access JWT가 아님 |
| 413 | `HTTP_PAYLOAD_TOO_LARGE` | `PAYLOAD_TOO_LARGE` | 본문이 서버 JSON 크기 한도를 넘음 |
| 429 | `HTTP_TOO_MANY_REQUESTS` | `TOO_MANY_REQUESTS` | 같은 설치 ID 또는 클라이언트 IP의 요청 제한 초과 |
| 500 | `INTERNAL_SERVER_ERROR` | `InternalServerError` | 예상하지 못한 오류 |

없는 작품, 발급되지 않은 세션, 범위를 벗어난 시각, 형식이 맞지 않는 개별 이벤트는 오류가 아니라 해당 이벤트를 버리는 것으로 처리한다. 이 API에는 개발 환경 제한이 없다.

### 노출 규칙

- 응답 본문이 없다. 저장 여부, 버린 이벤트 수와 사유, 집계 값, 다른 기기나 사용자의 기록을 반환하지 않는다.
- 내부 숫자 ID는 요청에 받지도 응답에 내보내지도 않는다. 재생 세션 ID는 발급받은 요청자에게만 응답하는 무작위 UUID다.
- 일별 집계는 관리자 사이트가 DB에서 직접 읽는다. 지표를 조회하는 공개 API는 두지 않는다.
- 앱은 이 API의 오류를 사용자에게 표시하지 않는다.

### 보관과 개인정보

- 저장하는 값: 설치 ID, 로그인했을 때의 사용자, 작품·회차·영상(재생은 서버가 세션에서 정함), 빼꼼 카드 순서, 이벤트 시각, 누적 시청 시간, 가장 먼 도달 위치.
- 저장하지 않는 값: 기기 고유번호, 광고 ID, IP 주소(요청 제한 카운터에서만 잠깐 쓴다), User-Agent.
- 설치 ID나 사용자 ID가 들어간 원본(노출·재생 세션)은 90일 뒤 지운다. 개인 식별자가 없는 일별 집계는 계속 보관한다.
- 탈퇴하면 그 사용자 ID가 들어간 원본과, 그 원본에 나온 설치 ID의 비로그인(`user_id`가 NULL) 원본을 지운다. 같은 기기에서 로그아웃 상태로 남긴 기록까지 지우기 위해서다. 그 기기를 함께 쓴 다른 사람의 비로그인 기록도 지워질 수 있지만, 지워지는 것은 원본 분석 기록뿐이고 고정된 집계는 바뀌지 않는다. 다른 로그인 사용자의 행은 지우지 않는다.
- 설치 ID 기준으로 삭제를 요청하면 그 설치 ID의 원본을 지운다.
- 탈퇴 처리 흐름(사용자 상태 변경)은 아직 없다. 탈퇴를 구현하는 작업에서 이 삭제를 함께 붙인다.
- 비로그인 사용자까지 수집하므로 설치 ID와 시청 기록 수집을 개인정보 처리방침에 적는다(수집 항목, 목적, 보관 기간 90일). 동의가 필요한지는 법무 확인 전이다.

### 앱 전송 규칙

- **노출:** 빼꼼 카드가 화면의 50% 이상을 차지한 채 1초 이상 머무르면 한 번 보낸다(추천). 빼꼼은 카드 하나가 화면을 채우므로 그 카드가 활성 카드로 확정되고 화면이 포커스된 채 1초가 지난 경우와 같다. 미리 불러 둔 카드와 홈·랭킹·찾기의 포스터 카드는 보내지 않는다.
- **전송 화면:** 포커스된 본편 재생 화면만 재생 이벤트를 보낸다. 다른 화면으로 이동해 스택 아래에 남은 재생 화면은 보내지 않는다.
- **재생 시작:** 본편 재생 화면에서 첫 장면이 실제로 표시되면 `playback_start`를 한 번 보낸다. `playback_progress`와 `playback_end`는 그 세션의 `playback_start`를 보낸 뒤에만 보낸다. 첫 장면 전에 화면을 떠나거나 오류가 나면 그 세션의 이벤트를 보내지 않는다.
- **재생 진행:** 재생 중 10초마다(제안값), 그리고 일시정지와 백그라운드 전환 때 `playback_progress`를 보낸다.
- **재생 종료:** 뒤로 가기, 다음 화, 작품 소개·회차 목록 같은 다른 화면 이동으로 재생 화면이 포커스를 잃을 때와 재생 오류가 났을 때 `playback_end`를 보낸다. 그 뒤로는 그 세션의 이벤트를 보내지 않는다. 다시 포커스되면 [재생 세션 ID 발급](#재생-세션-id-발급)대로 새 세션을 받는다.
- **시청 시간:** `watchedMs`는 실제로 재생된 시간의 합이다. 일시정지·탐색·버퍼링 시간은 넣지 않는다. 스토리보드 재생 화면에서는 장면이 화면에 떠 있던 시간이다.
- **도달 위치:** `maxReachedMs`는 정방향으로 이어서 재생해 도달한 가장 먼 위치다. 마지막 장면까지 보았거나 끝 카드가 뜨면 재생 API가 응답한 `durationMs`를 보낸다(추천).
- **장면형 플레이어:** 현재 앱의 본편 재생 화면은 영상 플레이어이므로 위치는 영상 재생 위치다. 장면·끝 카드·스토리보드 문구는 정의서의 추천안을 옮긴 것이며, 장면형 플레이어가 생기면 `durationMs`와 위치의 의미를 다시 정한다.
- **묶음 전송:** 이벤트를 모아 10~15초마다, 그리고 백그라운드 전환과 재생 종료 때 보낸다. 오프라인이면 기기에 쌓아 두었다가 다시 보낸다. 48시간이 지난 이벤트는 보내지 않고 버린다.
- **보낸 시각:** `sentAt`은 실제로 보내는 시도마다 새로 정한다. 처음 시도의 값을 다시 쓰면 보정 시각이 재시도 지연만큼 미래로 밀린다.
- **웹 페이지 이탈:** 웹은 페이지를 떠날 때 `fetch`의 `keepalive`로 보낸다. 이 요청은 JSON 본문 때문에 CORS preflight가 필요하고, preflight가 필요한 keepalive 요청은 브라우저마다 지원이 달라 유실될 수 있다. 204를 받기 전에는 큐에서 지우지 않으므로 다음 실행 때 다시 보낸다. 다시 보내도 결과가 같다.
- **응답 처리:** 204면 큐에서 지운다. 400·413이면 그 묶음을 버린다. 401이면 [공통 갱신 규칙](../00-overview/error-code.md#갱신세션-정리)대로 한 번 갱신해 다시 보내고, 그래도 401이거나 갱신할 수 없으면 그 묶음을 `Authorization` 없이 다시 보낸다. 재생 세션의 사용자는 발급 때 정해지므로 노출의 `user_id`만 비게 된다. 이 API의 401로는 세션 만료 안내를 띄우지 않는다. 429·5xx·네트워크 오류면 큐에 남기고 간격을 늘려 다시 보낸다.
- **사용자:** 이벤트마다 기록 당시의 로그인 사용자를 큐에 함께 둔다. 기록 당시 사용자가 현재 로그인 사용자인 이벤트만 `Authorization`을 붙여 보내고, 다르거나 기록 당시 비로그인이었으면 `Authorization` 없이 보낸다. 한 묶음에는 `Authorization`을 붙일 이벤트와 붙이지 않을 이벤트를 섞지 않는다.

### 구현할 때 같이 고칠 곳

이 계약을 구현하는 작업에서 함께 바꾼다.

- [회차 재생 API](../04-playback/episodes.md): `playbackSessionId`(IP 한도를 넘으면 `null`), `Cache-Control: no-store`, 세션 행 생성을 반영한다.
- [공통 규칙](../00-overview/conventions.md#미디어와-인증): 선택 JWT endpoint 목록에 `POST /analytics/events`를 더한다.
- `back/test/api/playback.postman_collection.json`: 재생 응답 `exactKeys` 목록에 `playbackSessionId`를 더한다. 키를 정확히 검사하므로 하위 호환 필드 추가도 그대로 두면 실패한다.
- `back/test/api/fixtureContext.mjs`: 재생 API GET이 공유 개발 DB에 `playback_sessions` 행을 만들므로 정리 대상에 더한다. 익명 요청이 만든 행은 `user_id`가 NULL이라 사용자 기준 정리로 지워지지 않으므로, 실행이 받은 세션 ID로 지우는 방법을 함께 정한다.
- 모듈 의존: 세션 발급은 content 모듈의 재생 API(`PublicCatalogService`)가 analytics 테이블에 쓰는 일이다. content가 analytics 서비스를 주입받는 방식 등 의존 방향을 정하고 [ARCHITECTURE.md](../../ARCHITECTURE.md)에 반영한다.
- CORS: 대상 브라우저의 preflight keepalive 지원과 preflight 캐시(`Access-Control-Max-Age`, 지금은 설정 없음)를 확인한다. 캐시가 없으면 10~15초마다 보내는 요청마다 preflight가 한 번 더 나간다.
- 관리자 사이트와 집계 작업은 [데이터 모델 제안](data-model-proposal.md#관리자-사이트-읽기)을 본다.
