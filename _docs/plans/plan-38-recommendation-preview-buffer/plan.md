# plan-38-recommendation-preview-buffer

## 목표
추천 피드의 이전·현재·다음 영상에 기존 미리보기 재생 API로 서명 URL을 요청하고, 최대 3개의 플레이어와 버퍼를 유지한다. 페이지 이동 시 준비된 플레이어를 재사용해 재생 시작 지연을 줄인다.

## 승인된 범위와 가정
- 프론트 추천 화면과 추천 전용 재생 상태 관리, 관련 회귀 테스트만 변경한다. 범위 승인과 task 구성 승인을 받았다.
- 인접 범위에 남아 있는 영상은 URL을 재요청하거나 플레이어를 재생성하지 않는다. 1→2 이동 시 1·2번을 유지하고 3번만 요청한다. 2→1 복귀 시 새 요청 없이 기존 1번을 처음부터 재생한다.
- 같은 focus 수명 안에서는 작품 UUID·preview UUID별 진행 중 URL 요청을 공유한다. 범위 밖으로 나갔다 요청 완료 전에 돌아와도 같은 요청을 재사용한다. 응답 순서가 아니라 현재 보관 항목과 마지막 확정 페이지로 결과 적용·재생을 결정한다. 오래된 settle 타이머·요청·플레이어 이벤트는 현재 페이지를 바꾸거나 과거 영상을 재생하지 못한다.
- 스크롤 중에는 재생만 멈추고 마지막 확정 페이지 주변의 플레이어를 유지한다. 페이지 확정 후 보관 범위를 이동한다.
- 다른 영상으로 페이지 이동이 확정되면 기존 영상을 `pause()`하고 재생 위치를 `currentTime = 0`으로 초기화한다. 인접 범위 안에서는 플레이어·URL·남아 있는 버퍼를 유지하며, 다시 돌아오면 0초부터 재생한다. 스크롤 취소나 같은 페이지의 중복 확정은 위치를 초기화하지 않는다.
- 범위 밖 플레이어와 리스너를 해제한다. 화면 blur/unmount 시 전부 정리하고 복귀 시 필요한 인접 범위를 새로 준비한다.
- 웹은 실제 HTML 영상 요소가 버퍼를 보유하므로 플레이어뿐 아니라 인접 VideoView의 안정적인 마운트도 유지한다. FlatList 가상화나 활성 카드 변경이 남아 있는 영상 요소를 재생성하지 않게 한다.
- 버퍼 보존량과 선로딩 여부는 플랫폼·브라우저·네트워크에 영향을 받는다. 영상 전체 저장이나 모든 이동에서 즉시 재생을 보장하지 않는다.

## 비목표 및 레이어
- 변경 레이어: `front/src/features/playback/`, `front/src/screens/`, `front/tests/`, 기존 프론트 테스트 실행 스크립트.
- 백엔드 REST 계약, API 문서, Postman 컬렉션, DB, 본편 재생, 영구 파일 캐시, 전역 캐시와 새 패키지는 변경하지 않는다.
- 기존 디렉터리 책임 안의 기능 추가이므로 아키텍처 문서 변경은 필요하지 않다.
- 기존 정렬·초기 작품·세로 스와이프·포스터 대체 화면·재생 컨트롤·구매 및 내비게이션 동작을 유지한다.

## 실행 순서 및 병렬 작업
- `task-1`은 `depends_on: []`이며 구현 완료 상태를 유지한다.
- 상태 관리와 화면 연결 및 테스트를 한 task에서 순서대로 구현하고 함께 검증한다. 플레이어 수명과 스크롤 이벤트가 직접 연결되어 있어 별도 병렬 task로 분리하지 않는다.
- `task-2`는 `depends_on: ["task-1"]`로 순차 실행한다. task-1에서 만든 영상 레이어의 터치 구조를 수정하며 화면·테스트 파일이 겹치므로 병렬 실행하지 않는다.

## 추가 수정 범위: task-2
- 사용자 요청으로 리뷰의 P1 스와이프 차단 문제를 수정하는 task를 추가한다. 기존 task-1의 완료 기록은 변경하지 않고 추가 task 실행을 위해 플랜을 draft로 되돌린다.
- 전체 화면 Pressable을 가진 컨트롤이 FlatList의 형제 레이어에 있어 목록이 터치 드래그를 처리하지 못하는 구조를 수정한다. 영상 요소만 비대화형 형제 레이어에 유지하고, 컨트롤은 각 목록 카드 안으로 옮긴다.
- 영상 레이어를 목록 아래에 배치하고 활성 카드의 배경·포스터가 영상을 가리지 않도록 처리한다. 스크롤 중·재생 불가 상태의 포스터 대체 화면과 기존 카드 폭 제한을 유지한다.
- URL 요청·버퍼 관리·백엔드 계약·새 제스처 라이브러리는 변경하지 않는다.
- 검증은 기존 자동 검사 3개와 목록/컨트롤 계층 회귀 검사, 실제 터치 스와이프 확인으로 구성한다. 모의 스크롤 콜백 검사를 실제 제스처 전달 검증으로 보고하지 않는다.

## 검증 및 완료 기준
- 자동 검증: `npm --prefix front run typecheck`, `npm --prefix front run test`, `npm --prefix front run export`.
- 제어 가능한 지연 응답과 fake player를 사용해 URL 요청 수, 플레이어 객체 동일성, 재생·정지·해제, 늦은 응답 무시를 검증한다. 화면 이벤트 연결과 안정적인 VideoView 유지도 같은 테스트 파일에서 검증한다.
- 요청 미완료 상태의 반복 왕복은 같은 영상에 HTTP 요청 1개만 유지해야 한다. 1→2→3 이동 뒤 응답을 역순으로 완료하고 오래된 settle 콜백을 실행해도 마지막 확정 페이지가 유지되고 그 영상만 재생돼야 한다.
- 1번을 재생 도중 2번으로 넘겼을 때, 2번 재생 전에 1번이 정지·0초 초기화되며 플레이어가 유지되는지 확인한다. 1번으로 복귀하면 같은 플레이어가 0초부터 재생되어야 한다.
- 실제 화면에서는 1→2→1, 1→2→3, 빠른 연속 이동, 스크롤 취소, 탭 이탈·복귀를 확인한다. 한 영상만 소리가 나야 하며 남아 있는 영상의 플레이어·영상 요소가 재생성되지 않아야 한다.
- 실제 화면 검증은 기존 프론트 `http://localhost:8081`, 백엔드 `http://localhost:3000`에 먼저 HTTP로 연결을 확인한 뒤 수행한다. 서버를 추가로 실행하거나 다른 포트를 사용하지 않는다.
- 서버가 없으면 해당 실화면 검증은 실패로 기록한다. 사용자에게 프론트 `npm --prefix front run start -- --port 8081`, 백엔드 `npm --prefix back run start:dev`를 안내한다. 자동 검증 결과와 구분하고 실화면 검증을 통과로 보고하지 않는다.
- 계획 작성 단계에서는 제품 코드 변경이나 제품 검증을 실행하지 않았다. 계획 파일 검증 결과는 아래에 기록한다.
